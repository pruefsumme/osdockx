# Dock hover optimization results

Functional baseline: `6b2eea9`

Hover-stabilization implementation: `48e1770` through `fb6246c`

This report retains the earlier renderer baseline and records every live result reproduced during the hover-stabilization work. A power outage interrupted the final soak, changed the live desktop session, and removed the temporary reports. Values below were copied from the reports before the outage; the accepted full report was `/tmp/osdockx-perf-124508-1786745235.txt`.

## Hover scheduling behavior

GTK motion events now wake one shared frame callback. On X11, `XQueryPointer` root coordinates are converted through the last applied physical dock geometry and scale factor, so widget-relative motion generated by window movement cannot become authoritative hover input. An unchanged root sample produces no new layout or paint. Non-animation work stops after one frame; only a live time-based animation can retain the callback.

Paint-only magnification frames do not invoke window geometry, strut, or shape synchronization. X11 model updates are classified so title, PID, and minimized-state churn that does not affect dock output does not repaint or synchronize. A stable visual-only label envelope prevents label crossings from reshaping the window while leaving input regions unchanged.

Permanent counters cover motion events, frame ticks, visible layout changes, paint requests, completed redraws, window synchronizations, shape updates, animation frames, and model-update classes. They are available in ten-second debug summaries and through the helper's on-demand X11 snapshot protocol.

## Accepted live phase run before the outage

The release build was installed with `install.sh`, warmed for two minutes, and sampled for four 60-second phases on the existing 64px-style dock geometry (`889,1584,1102,216`). Passive phases used a reported two-second transition-settling interval. The controlled sweep used a reported 2.0 pointer samples per second; this rate is part of the result and must not be omitted when comparing it.

| Phase | Dock CPU | Xorg CPU | Paints | Window syncs | Shape updates | PSS | Private |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Warm-up | 6.100% | 59.699% | 19 | 0 | 0 | 68,969 KiB | 49,252 KiB |
| Stationary hover | 1.300% | 60.033% | 0 | 0 | 0 | 68,921 KiB | 49,204 KiB |
| Controlled sweep | 6.983% | 59.450% | 120 | 0 | 0 | 68,991 KiB | 49,272 KiB |
| Post-sweep idle | 1.317% | 62.900% | 0 | 0 | 0 | 69,447 KiB | 49,728 KiB |

Stationary and idle phases also recorded zero motion events, frame ticks, visible layout changes, and animation frames. The sweep recorded 120 motion events, frame ticks, visible layout changes, paints, and redraws, demonstrating one paint-only frame per controlled pointer sample without movement, reshape, or strut work. Xorg sweep CPU was 3.45 percentage points below post-sweep idle in the same run. Phase private growth was 2.778% and PSS growth was 1.979%.

The ten-minute soak started immediately afterward at 49,728 KiB private memory. It reached minute 9 at 49,880 KiB (+0.306%) with the same PID and no upward trend. The power outage occurred before minute 10, so this is not claimed as a completed ten-minute pass.

## Failed measurements retained for traceability

The helper and runtime were corrected in response to these live failures:

| Run | Result | Cause or disposition |
| --- | --- | --- |
| Initial 60 s phase run | ~27% dock CPU and 601 paints/syncs/shapes | Nonvisual X11 metadata churn rebuilt output; fixed by visual/presence classification. |
| Centerline helper | 1.6% stationary, no controlled hover paints | Centerline missed the shaped icon lane; helper now derives the lane from X Shape. |
| Approximately 60 Hz sweep | 90.4% dock CPU; average Cairo draw 2.193 ms | GTK surface/compositor submission dominated; retained as a failed high-rate result. |
| 4 Hz sweep | 14.2% dock CPU | Failed the 10% sweep gate. |
| 2 Hz short run | 1.5% stationary, 9.2% sweep | Passed CPU/memory gates and established the explicit controlled rate. |
| Full run before passive settling | 3.133% stationary with 48 paints/21 syncs | Bounded entry animation was included in the passive phase; helper now settles for two seconds before passive snapshots. |
| Full sweep to window ends | 8.017% sweep with 30 syncs | Path crossed rounded input-shape ends; helper now uses inset bounds from the longest input rectangle. |

After the reboot, the user configuration changed at 11:35 to `icon_size = 128`; it was preserved. The resulting dock geometry was `-517,1154,2880,646`, rather than the accepted run's 1102×216 geometry. First hover faulted large Mesa/LLVM and surface mappings into memory. A default-renderer candidate reached 190,713 KiB PSS and 171,852 KiB private memory; a `GSK_RENDERER=cairo` experiment still mapped Mesa/LLVM and ended at 183,797 KiB PSS and 165,564 KiB private memory. The exact pre-change `ca17571` binary also measured 159,448 KiB PSS and 141,124 KiB private memory in that cold session, with 82 MiB attributed to clean `libLLVM` mappings. These post-reboot measurements fail the absolute memory gates and are not presented as optimization results.

Because the cold-session gate failed, the installed binary was rolled back to the exact pre-change build (SHA-256 `52c5a12003f5e5e85f2feaa911e8ace0cd0e46fc150c56f21bd056114611871e`) and restarted. The changed user config was not reverted. The final candidate is preserved locally at `/tmp/osdockx-final-candidate-fb6246c` for follow-up validation.

## Reproduction

Run:

```text
cargo fmt --check
cargo test renderer_paints_non_empty_surface --lib
cargo test renderer::tests::leopard --lib
cargo test --lib
cargo test --bin osdockx-perf
cargo bench --bench cairo_renderer
```

For live measurements, install a release build, preserve a checksum of the current config, warm for two minutes, and run `osdockx-perf <PID> 60`. The helper discovers the dock through EWMH client lists, translates reparented geometry to root coordinates, restores the original pointer on success or failure, and writes its report under `/tmp`.
